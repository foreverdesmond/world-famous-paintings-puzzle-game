## 1. 设计目标与结论

V1 采用单页 React + TypeScript 应用。核心游戏规则以不依赖 React 的纯函数实现；界面层只负责驱动会话状态、渲染拼图和响应用户操作。这样难度计算、打乱、交换、完成判定与计时语义可以被独立测试，图片资源清单可独立校验，不影响游戏逻辑。

图片真源为 `assets/paintings/` 的 101 张随应用交付的静态图片及 `manifest.csv`。一轮固定为 100 关，但图库可大于 100 张；后续扩图不改变关卡数。应用运行时不抓取、不上传或修改外部资源。

本设计不包含账号、存档、排行榜、后端、原生应用封装、拖拽操作或在线图库管理。

工程初始化选用 Vite、React、TypeScript、Vitest 和 React Testing Library；这是无后端的新项目中成熟且轻量的组合，不改变已审核的用户可见需求。

## 3. 系统上下文与影响范围

```text
静态图片清单 + 本地图片
          │
          ▼
    游戏会话控制器 ─────► 纯规则函数
          │                    │
          ▼                    ▼
  React 游戏页面       难度 / 打乱 / 交换 / 完成判定
          │
          ├── 左：原图提示或拼图棋盘
          └── 右：关卡、计时、作品信息、结果或故障操作
```

运行时没有服务端、数据库、后台任务或第三方 API。浏览器是唯一运行入口；刷新、关闭页面或选择退出都会丢弃会话状态。

## 4. 静态资源与数据契约

### 4.1 图片清单

应用通过版本管理的 `manifest.csv` 读取图片，并在构建期转换为类型化应用清单。资源接入任务不再创建占位图；它负责将现有 CSV 映射为应用数据、读取本地图片尺寸，并输出可审计的校验结果。

```ts
type Artwork = {
  id: string;
  title: string;          // 英文原名
  titleZh: string;        // 中文译名
  artist: string;         // 英文原名
  artistZh: string;       // 中文译名
  date: string;           // 未知时为“年代未知”
  imagePath: string;
  width: number;
  height: number;
};
```

`id` 由 `file` 的文件名（去除扩展名）稳定派生。加载前校验：`id` 唯一、图片路径非空、宽高为正数，`titleZh` 与 `artistZh` 非空。`date` 缺失时赋值“年代未知”；`width`、`height` 由本地图片读取。英文原名来自 `manifest.csv`，中文译名由项目内版本管理的本地映射提供。原始 CSV 的 `institution` 映射为资源维护记录的 `sourceProvider`，而非 `Artwork` 的馆藏机构；来源 URL、图片 URL、许可证和 `sourceProvider` 不进入游戏 UI 契约。完整游戏要求至少有 100 条可加载记录，且包含两张固定练习图。

### 4.2 图片方向

`width >= height` 为横版（正方形归入横版），否则为竖版。方向只影响行列分配，不影响同一 Level 的拼块总数。

## 5. 领域规则

### 5.1 关卡与会话模型

```ts
type Tile = {
  id: number;             // 原图中的唯一切片编号
  correctIndex: number;   // 正确位置，从 0 开始
};

type Board = {
  rows: number;
  columns: number;
  tiles: Tile[];          // 数组下标即当前显示位置
};

type GameSession = {
  stage: number;          // 1 至 100
  usedArtworkIds: Set<string>;
  artwork: Artwork;
  board: Board;
  selectedTileIndex: number | null;
  startedAtMs: number | null;
  finishedAtMs: number | null;
};
```

第 1 关固定使用 `mona-lisa__leonardo-da-vinci`，第 2 关固定使用 `the-starry-night__vincent-van-gogh`，并立即加入 `usedArtworkIds`。第 3–100 关从合格清单中排除 `usedArtworkIds` 后随机选择一张，并立即加入集合。完整游戏因此恰好使用 100 张不同图片，但不要求用尽图库；后续增加的合格图片会自然扩大随机选择池。

### 5.2 难度计算

- 第 1、2 关固定为 2 行 × 2 列。
- 第 3 关起，正式 Level 为 `L = floor((stage - 3) / 5) + 1`。
- 横版/正方形：`rows = floor((L + 4) / 2)`，`columns = floor((L + 5) / 2)`。
- 竖版：交换上述行列数。

| 关卡 | 横版/正方形 | 竖版 |
| --- | --- | --- |
| 1–2 | 2×2 | 2×2 |
| 3–7（Level 1） | 2×3 | 3×2 |
| 8–12（Level 2） | 3×3 | 3×3 |
| 13–17（Level 3） | 3×4 | 4×3 |
| 98–100（Level 20） | 12×12 | 12×12 |

### 5.3 打乱、交换与完成判定

1. 按 `0..rows*columns-1` 创建正确顺序切片。
2. 用 Fisher–Yates 洗牌生成排列；若排列仍为正确顺序或错位数小于 `ceil(tiles.length × 0.5)` 则重新洗牌。
3. 因初始布局是正确排列的置换，任意局面都可通过有限次两两交换恢复；最低错位比例为 50%，避免高难关只错少数切片。
4. 用户首次点击：保存当前索引为 `selectedTileIndex`，但不交换。
5. 再次点击同一索引：清空选中状态，不交换。
6. 点击不同索引：交换 `tiles` 中两个元素，清空选中状态，并检查每个 `tiles[index].correctIndex === index`。
7. 所有切片正确即通关。

## 6. 界面与状态设计

### 6.1 顶层状态

```text
开始新游戏
  → 加载图片
  → 原图提示（固定 5 秒，不可操作、不计时；结束后不可再次查看）
  → 拼图进行中（未选中 / 已选中）
  → 本关完成
     ├→ 下一关（第 1–99 关）
     └→ 最终通关动画（第 100 关）→ 退出游戏

加载失败：同一图片重试至多 5 次 → 游戏故障 → 退出游戏
```

“退出游戏”返回开始页并销毁当前会话；不保存关卡、用图记录或计时。

会话仅存在于 `useGameSession` 的内存状态。V1 不实现重开、重打乱或再次查看原图事件，也不读写 `localStorage`、`sessionStorage`、IndexedDB 或 Cookie；页面刷新与退出均创建全新会话。

### 6.2 页面布局

主页面在宽度不小于 1024 CSS 像素时使用两列布局：左侧是主要拼图画布，右侧是信息面板。移动设备仅在横屏且宽度不小于 640 CSS 像素时提供拼图区优先的单列布局；竖屏或宽度不足时只显示“请横向旋转设备后继续游戏”提示，不渲染可操作切片。

计时状态组固定包含“第 `stage` / 100 关”、练习关或正式 Level 标识与实时耗时；三项必须在同一区域同时可见。信息面板其余内容仅为作品名、作者和年代。作品名显示“中文 / English”，作者显示“中文 / English”；年代缺失时显示“年代未知”。游戏界面不显示馆藏机构、素材来源平台、来源、图片 URL 或许可证信息。横屏移动布局中计时状态组必须保持可见；作品信息不得覆盖棋盘。

拼图棋盘以 CSS Grid 渲染，棋盘容器 `aspect-ratio` 必须等于原图 `width / height`，不得固定为正方形。每块切片使用同一原图作为背景图，通过与棋盘相同的比例和背景位置显示其正确的原图区域；`tile.correctIndex` 决定背景位置，数组索引决定当前格子位置。背景不得拉伸、`cover` 裁切或省略边缘内容；这样交换时只改变数组位置，不创建或裁切额外图片文件。

### 6.3 计时

首次有效切片点击记录 `performance.now()`；每 250ms 刷新一次显示值。通关时记录结束时间并停止刷新。计时使用经过时间而非累加计数，因此浏览器短暂卡顿不会少计；V1 不提供暂停，切换标签页期间时间继续流逝。

显示规则：少于 60 秒为 `XX秒`；达到 60 秒为 `XX分XX秒`，秒数向下取整。

### 6.4 图片加载失败

预加载当前图片。失败时重新加载同一 URL，最多总计 5 次；每次间隔递增。第 5 次失败后进入故障状态，显示“游戏故障”，唯一可用按钮为“退出游戏”。不得替换为另一幅图片，不得继续使用半加载棋盘。

每次关卡创建时生成单调递增的 `loadRequestId`。图片成功、失败或重试回调只在其 `loadRequestId` 仍等于当前会话值时才能更新状态；退出、开始下一关或组件卸载时使当前编号失效并清除计时刷新器。浏览器已经发出的图片请求可以在网络层自然结束，但其迟到结果不得重新打开旧关卡。

### 6.5 动画与可访问性

- 选中切片：边框/阴影和轻微缩放，过渡不超过 160ms。
- 交换：位置变化使用约 180–240ms 的 transform 过渡；动画不得拦截下一次点击。
- 原图提示、结果面板和最终通关使用约 200–300ms 的淡入淡出。
- 切片以可聚焦按钮实现，提供包含作品名和当前位置的辅助文本；同一点击事件同时支持鼠标点击与触屏轻触，且不依赖悬停；结果和退出按钮必须可键盘操作。
- 尊重 `prefers-reduced-motion`：关闭非必要位移动画，保留状态可见性。

## 7. 错误、边界与安全

| 情况 | 行为 |
| --- | --- |
| 图片清单为空 | 不开始游戏，显示不可用状态与退出操作。 |
| 合格清单少于 100 条、缺少固定练习图或中英映射 | 不进入完整一轮游戏；仅允许在受控测试中使用测试清单。 |
| 移动设备竖屏或横屏宽度不足 640px | 显示旋转/尺寸提示，不渲染可操作拼图。 |
| 同一切片再次点击 | 取消选中。 |
| 预览期点击 | 忽略，不开始计时。 |
| 图片加载连续 5 次失败 | 显示故障，只能退出。 |
| 第 100 关完成 | 播放基础动画后只能退出。 |
| 刷新/关闭页面 | 丢弃会话，无恢复。 |
| 请求重开、重打乱或再次查看原图 | V1 不渲染入口，也不提供状态事件或隐藏快捷操作。 |

应用不接收用户文本、账号或秘密；不向外部服务发送游戏状态。资源来源、许可证和原图链接仅保留在仓库资源维护文件中，不进入前端 UI。

## 8. 配置、安全与可观测性

### 8.1 配置与安全

- V1 没有运行时秘密、账号、令牌、后端地址或用户数据；`N/A`：不引入环境变量和认证配置。
- V1 不读写 `localStorage`、`sessionStorage`、IndexedDB 或 Cookie 中的游戏状态；浏览器资源缓存不作为游戏状态真源。
- 运行时资源只允许项目内相对图片路径；资源维护清单中的外部链接不向游戏 UI 透出。
- 运行时不得执行外部图片抓取、上传或遥测；现有素材的许可证字段只在资源维护清单中保留，不进入 UI，也不执行外部核验。

### 8.2 可观测性

- V1 不接入远程日志、分析或错误上报服务；这是避免额外隐私与外部依赖的明确范围限制。
- 开发环境可向浏览器控制台输出带 `stage`、`artworkId`、`attempt` 的图片加载失败诊断；不得输出用户数据或秘密。
- 用户可见状态是本版本的主要诊断面：加载中、故障、关卡完成和最终完成均必须有明确界面状态。

## 9. 性能与资源影响

- 同一关只预加载一张图片并以 CSS 背景重复显示，不生成单独切片文件；棋盘状态仅保存切片数组，空间复杂度为 `O(rows × columns)`，最高为 144 块。
- 计时器每 250ms 更新一次；不在每帧重建棋盘或重新洗牌。
- 开发与真实图库图片的交付尺寸应以最长边约 1200–1600 CSS 像素为目标；实际选图任务必须核验图片在 12×12 棋盘中的可辨识度。
- 1024×768 桌面视口与 640×360 横屏移动视口的 12×12 棋盘是人工 Level 2 验证项；若不可读，先记录截图/录屏与触屏证据，再由项目负责人通过变更请求决定调整 CSS 布局或难度规则，编码 Agent 不得自行改变难度公式。

## 10. 组件职责与依赖方向

| 组件 | 职责 | 依赖 |
| --- | --- | --- |
| `gameRules` | 难度、图片选择、打乱、交换、完成判定和耗时格式化 | TypeScript 标准库、随机数/时钟抽象 |
| `artworkCatalog` | 读取、合并中英映射并校验图片清单 | 静态 JSON/模块 |
| `useGameSession` | 管理顶层状态、预览、计时、重试和流程跳转 | `gameRules`、`artworkCatalog`、浏览器时钟 |
| `PuzzleBoard` | 渲染棋盘与转发切片点击 | `Board`、图片路径、回调 |
| `GameSidebar` | 渲染计时、关卡、作品名、作者与年代 | 会话只读状态 |
| `ResultDialog` | 渲染本关完成、最终完成或故障状态 | 回调 |
| `GamePage` | 组合页面与开始/退出入口 | 上述 UI 组件 |

运行时调用方向为 `GamePage → useGameSession → gameRules/artworkCatalog`，UI 子组件仅经回调上报用户意图。`gameRules` 不依赖 React、CSS 或浏览器 DOM。编译时依赖同向，资源访问细节不进入规则模块。

## 13. SOLID 审查

- **S**：规则、资源清单、会话控制与呈现组件拥有独立变化原因。
- **O**：图片来源可通过替换 `artworkCatalog` 扩展；规则不依赖特定馆藏来源。
- **L**：开发清单与真实清单均满足同一 `Artwork` 契约。
- **I**：展示组件只接收它们需要的只读数据和回调。
- **D**：核心规则仅依赖数据和时钟/随机数抽象；React 与资源加载位于边界层。
